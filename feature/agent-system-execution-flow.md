最关键判断
  当前后端的目录边界设计是合理的，但运行时边界没有真正闭环。
  最突出的问题不是缺少类或模块，而是：
设计上已经有 Policy（策略）、RunService（运行生命周期服务）、Checkpoint（检查点）和 ToolRuntime（工具运行管线），但真实执行路径绕过了
其中一部分。

  也就是说，当前系统是“架构概念基本齐全，执行权仍然分散”。

二、P0：工具执行绕过了统一控制边界
  这是目前最严重的问题。
  设计中已经存在 ToolRuntime（工具运行管线）：
  app/harness/execution/pipeline.py
  它准备承担：
- 行动检查；
- 副作用识别；
- 幂等控制；
- 行动预记录；
- 产物登记；
- 观察结果标准化。
  但是实际的智能体执行路径是：
  BoundedReActExecutor（有界推理与行动执行器）
  → ToolRunner（工具运行适配器）
  → ToolBroker（工具代理）
  → MCP（模型上下文协议）或脚本
  app/harness/react/executor.py:316-339 中，工具通过：
  results = await self._tools.execute(state.pending_calls)
  直接进入 ToolBroker（工具代理）。
  目前没有生产代码实例化 ToolRuntime（工具运行管线）。它基本只存在于单元测试和设计结构中。
直接后果
  真实执行路径没有统一执行：
- 副作用分类；
- 高风险行动审批；
- 行动预记录；
- 幂等键写入；
- 产物正式登记；
- 副作用工具串行化；
- 可恢复执行。
  check_action（行动检查）现在只检查：
- 工具是否存在；
- 是否在阶段白名单中；
- 参数结构是否合法；
- 是否重复且无进展。
  它没有接收：
- 当前账号；
- 当前身份；
- 当前会话；
- 数据访问范围；
- 风险级别；
- 审批状态；
- 工具授权凭证。
  所以这里的 allowed_tools（允许工具）实际上只是“阶段工具白名单”，不是安全意义上的授权。
应有边界
  必须只允许一条执行路径：
  模型行动提议
  → ActionGateway（行动网关）
  → 参数校验
  → 身份与权限检查
  → 风险和审批检查
  → 持久化待执行行动
  → 环境执行
  → 持久化执行结果
  BoundedReActExecutor（有界推理与行动执行器）不应该直接持有能够执行工具的 ToolRunner（工具运行适配器），只应该依赖一个统一的
  ActionGatewayPort（行动网关端口）。
  ———
三、P0：副作用预记录的顺序反了
  即使未来直接接入现有 ToolRuntime（工具运行管线），它目前的顺序也存在严重问题。
  在：
  app/harness/execution/pipeline.py:199-221
  当前顺序是：
  发送工具开始事件
  → 执行 ToolBroker（工具代理）
  → 判断副作用类型
  → 保存 PlannedAction（计划行动）
  也就是先执行：
  app/harness/execution/pipeline.py:210
  然后才保存计划行动：
  app/harness/execution/pipeline.py:220-221
  这和正确顺序相反。
  正确顺序必须是：
  识别副作用
  → 生成幂等键
  → 保存计划行动
  → 提交检查点
  → 执行外部操作
  → 保存执行结果
  否则，如果进程在工具已经执行、计划行动尚未保存时崩溃，恢复后系统无法判断该操作是否已经发生，可能重复：
- 发消息；
- 写文件；
- 提交业务数据；
- 触发远程任务；
- 调用非幂等接口。

四、P0：运行持久化边界实际上没有落地
  RunService（运行生命周期服务）的抽象设计是合理的，它定义了：
- SnapshotStore（快照存储）；
- EventLog（事件日志）；
- RunLease（运行租约）；
- 创建、恢复、取消、完成和查询。
  但生产服务容器仍然固定使用：
- MemorySnapshotStore（内存快照存储）；
- MemoryEventLog（内存事件日志）；
- MemoryRunLease（内存运行租约）。
  位置：
  app/application/services.py:66-73
  这意味着：
- 服务重启后运行状态消失；
- 无法真正恢复运行；
- 多进程之间看不到彼此的运行；
- SSE（服务器发送事件）无法真正重连续传；
- 运行审计不持久；
- 多实例部署无法保证同一运行只有一个执行者。
租约也没有闭环
  RunLease（运行租约）定义了：
- 获取租约；
- 心跳续期；
- 释放租约；
- 请求取消。
  但是当前代码中：
- 没有调用心跳；
- 没有在完成或失败后释放租约；
- RunService.query（运行查询）和 RunService.resume（运行恢复）没有进入真实接口；
- 租约与实际执行任务之间没有稳定绑定。
  所以当前的租约更像接口占位，还不是有效的执行所有权边界。
正确定位
  应该明确：
- PostgreSQL（关系型数据库）保存运行快照和事件；
- Redis（内存数据存储）保存短期租约、取消信号和执行者心跳；
- 进程内 ActiveTurnRegistry（活动回合注册表）只能是本地优化，不能成为事实来源；
- RunService（运行生命周期服务）应成为运行状态的唯一权威入口。
  ———
五、P0：工作区隔离维度不合理
  当前工作区按智能体标识创建：
  workspaces/{agent_id}
  位置：
  app/environment/workspace/service.py
  调用位置：
  app/harness/agent_runner.py:168
  虽然装配方法接收了 account_id（账号标识）和 session_id（会话标识），但创建工作区时只使用：
  workspace = await self._workspaces.create(target.id or "")
  这意味着所有使用同一个智能体的：
- 不同账号；
- 不同会话；
- 不同运行实例；
  共享同一个可写目录。
  这不是单纯的目录组织问题，而是数据和并发边界错误。
可能产生的问题
跨账号泄漏
  用户甲生成的文件可能被用户乙后续运行读取。
并发覆盖
  两个会话同时使用同一个智能体，可能写入相同文件名。
产物归属错误
  脚本执行器通过比较执行前后的整个工作区来发现产物。两个会话并发写文件时，一个运行可能把另一个运行的文件登记为自己的产物。
恢复不确定
  无法根据工作区状态判断文件属于哪一个运行。
建议边界
  可写工作区至少应按照：
  workspaces/{account_id}/{conversation_id}/{run_id}
  隔离。
  智能体需要共享的只读内容，应单独放在：
  agent-resources/{agent_id}
  形成明确关系：
- 智能体资源：跨运行共享、只读；
- 会话工作区：账号或会话隔离、可写；
- 运行临时区：运行实例隔离、可清理；
- 正式产物：进入独立产物存储并记录所有权。
  ———
六、P0：模型生成结果被直接认定为任务完成
  当前 BoundedReActExecutor（有界推理与行动执行器）中的：
- phase_contract（阶段契约）；
- output_contract（输出契约）；
  并没有真正执行验证，主要只是把模型结果包装成：
- CANDIDATE_COMPLETED（候选阶段完成）；
- FINAL_PROPOSED（最终结果提议）。
  位置：
  app/harness/react/executor.py:406-438
  但在回合终态映射中：
  app/application/chat/run_turn.py:279-299
  下面三种结果都会直接变成成功：
- FINAL_PROPOSED（最终结果提议）；
- CANDIDATE_COMPLETED（候选阶段完成）；
- INPUT_REQUIRED（需要输入）。
  这意味着：
“模型提交了最终答案”和“系统验证最终答案成立”目前没有分开。

  其中最明显的语义错误是：
  INPUT_REQUIRED（需要输入）
  → succeeded（成功）
  → COMPLETED（已完成）
  需要用户补充输入，本质应该是：
  WAITING_INPUT（等待输入）
  而不是成功终态。
正确边界
  应该分为：
  模型提交候选结果
  → Verifier（验证器）
  → 通过：完成
  → 不通过但可修复：重新进入模型循环
  → 缺少输入：持久化挂起
  → 无法自动判断：人工审核
  → 不可恢复：失败或部分完成
  ———
七、P1：运行状态存在多个权威来源
  当前至少有四套状态同时描述一次执行：
1. ActiveTurnRegistry（活动回合注册表）
   描述当前进程中哪个会话正在执行。
2. RunService（运行生命周期服务）
   描述运行快照、终止状态、租约和事件。
3. ReactGraphState（推理图状态）
   描述实际模型循环、预算、工具调用和进展。
4. ConversationService（会话服务）
   描述用户最终能看到的消息状态和回复内容。
  这些对象分别有合理用途，但当前缺少明确的主从关系。
  例如：
- 推理图状态变化不会持续同步到运行快照；
- 运行快照中的预算并不是实际推理图预算的持续事实源；
- 会话消息可以落库为中断，但运行快照未必形成一致的中断终态；
- 进程内任务取消、持久化取消标记和图执行状态不是一个原子变化。
建议主从关系
  应明确：
  RunState（运行状态）是控制状态权威
  EventLog（事件日志）是历史事实权威
  ArtifactStore（产物存储）是产物权威
  Conversation（会话记录）是面向用户的投影
  ActiveTurnRegistry（活动回合注册表）只是进程内缓存
  ReactGraphState（推理图状态）只是当前步骤的执行状态
  会话记录不能代替运行状态，推理图状态也不能代替持久化运行状态。
  ———
八、P1：事件通道发生了分裂
  当前有两条事件通道：
持久事件
  由 RunService（运行生命周期服务）写入 EventLog（事件日志）。
  目前主要写入：
- 运行开始；
- 运行完成；
- 运行失败；
- 运行取消。
实时事件
  由 QueueEmitter（队列事件发送器）推送给 SSE（服务器发送事件）。
  包括：
- 模型调用；
- 工具调用；
- 思考增量；
- 文本增量；
- 进展变化。
  但实时事件没有统一写入持久事件日志。
  因此，当前 EventLog（事件日志）不能完整实现：
- 运行重放；
- 工具调用审计；
- 断线续传；
- 故障后恢复；
- 完整时间线查询。
  RunService.query（运行查询）虽然提供了按序号读取事件的接口，但当前没有真实调用入口。
建议
  所有领域级运行事件应先进入统一的 RunEventSink（运行事件出口）：
  运行事件
  → 分配序号
  → 持久化事件日志
  → 更新运行快照
  → 推送实时订阅者
  文本打字机分片可以不全部持久化，但下面这些必须持久化：
- 行动提议；
- 行动拒绝；
- 工具开始与完成；
- 审批请求与结果；
- 状态转移；
- 检查点；
- 终态。
  ———
九、P1：Context（上下文）边界放置不够准确
  当前：
  app/environment/context/
  同时包含：
- 上下文事实模型；
- 会话和附件来源端口；
- 历史裁剪；
- 摘要处理；
- 上下文组装；
- 系统消息投影。
  这里混合了两种不同职责。
属于 Environment（执行环境）的部分
- 会话历史来源；
- 附件来源；
- 证据来源；
- 文件与环境状态读取。
  这些回答的是“系统有哪些事实”。
属于 Harness（运行与控制框架）的部分
- 本轮选择哪些事实；
- 字符和令牌预算；
- 历史裁剪；
- 摘要回退；
- 技能与工具描述注入；
- 系统消息顺序；
- 投影为模型消息。
  这些回答的是“模型本轮可以看到什么”。
  因此：
- ContextAssembler（上下文装配器）；
- ContextProjector（上下文投影器）；
  本质上更接近 Harness Context Compiler（运行框架上下文编译器），不完全属于执行环境。
  建议拆成：
  environment/context_sources
      会话、附件、证据和环境事实来源
  harness/context
      选择、裁剪、压缩、注入和模型消息投影
  ———
十、P1：Harness（运行与控制框架）仍然直接依赖具体 Environment（执行环境）
  AgentAssembler（智能体装配器）位于：
  app/harness/agent_runner.py
  但它直接依赖并实例化：
- MCPManager（模型上下文协议管理器）；
- ScriptExecutor（脚本执行器）；
- WorkspaceManager（工作区管理器）；
- ToolBroker（工具代理）。
  这使得 Harness（运行与控制框架）同时承担了：
- 计算执行计划；
- 创建工作区；
- 创建工具代理；
- 激活远程服务；
- 绑定脚本执行器。
  与项目自己声明的“运行框架只执行计划、不识别具体能力实现”存在偏差。
建议边界
  Harness（运行与控制框架）只应依赖：
- CapabilityCatalogPort（能力目录端口）；
- ActionExecutorPort（行动执行端口）；
- WorkspacePort（工作区端口）；
- ArtifactPort（产物端口）；
- RunStorePort（运行存储端口）。
  具体的 MCP（模型上下文协议）、脚本、工作区和工具代理，应在 bootstrap（组合根）或专门的适配层完成装配。
  ———
十一、P2：脚本边界当前只能称为“可信脚本执行”，不能称为沙箱
  脚本执行做得比较好的地方包括：
- 不使用 Shell（命令解释器）；
- 使用参数数组；
- 用户输入通过结构化标准输入传递；
- 限制环境变量；
- 校验脚本声明；
- 限制输出；
- 处理超时和进程终止；
- 检查工作区路径。
  这些对于内部可信脚本是合理的。
  但脚本仍然使用宿主机当前进程身份直接执行，理论上可以访问该系统账号拥有权限的其他路径和网络。
  所以边界应明确表述为：
当前是 Trusted Script Execution（可信脚本执行），不是 Untrusted Code Sandbox（不可信代码沙箱）。

  由于在线管理目前不允许直接编辑 scripts（脚本）和 schemas（结构约束），且发布接口要求超级用户，当前风险有所控制。
  但如果未来支持：
- 第三方技能包；
- 用户上传技能；
- 插件市场；
- 不受完全信任的管理员；
- 动态生成脚本；
  就必须迁移到容器、受限系统账号或独立执行服务。
  ———
十二、哪些边界已经做得比较好
  以下部分建议保留，不需要推倒重来：
1. interfaces（接入层）基本只处理请求、响应和事件映射。
2. 模型输出已经转换成结构化 AgentDecision（智能体决策），没有直接用自由文本控制图跳转。
3. 智能体业务知识、评分规则和模板已经移出平台代码，放在智能体包中。
4. 工具使用限定名和分层暴露，避免全部工具结构常驻上下文。
5. 历史消息中的 system（系统角色）不会重新作为系统指令注入。
6. MCP（模型上下文协议）异常已经在客户端边界归一化，没有把底层网络对象泄漏到运行框架。
7. 预算和无进展检测由确定性代码控制，而不是交给提示词。
  ———
最终结论
  当前后端不是“架构分层错误”，而是：
静态代码边界已经比较清晰，但动态执行边界尚未统一。

  最优先需要收紧的四个地方是：
1. 所有工具执行必须统一经过 ActionGateway（行动网关），禁止推理图直接调用 ToolBroker（工具代理）。
2. 把运行快照、事件日志和租约替换成真正的持久化实现，并补齐心跳、释放和恢复。
3. 把工作区从智能体级共享改为账号、会话或运行级隔离。
4. 把模型候选结果、需要用户输入和真正完成拆成不同状态，由独立 Verifier（验证器）决定终态。
