# 客户账期评估 Skill

## 1. 概述与定位

本 Skill 是**电子信息产业链客户信用与账期授信评估工具**，不是通用企业查询工具。

**第一性原理**：天眼查/企查查告诉"这家公司是谁"，但销售经理真正需要回答的是——**"现在给这家客户放 N 天账期、M 金额信用额度，这笔应收账款的回收概率和坏账风险有多大？"**。账期决策的底层由四层事实决定：

| 层次 | 回答的问题 | 数据源 |
|------|-----------|--------|
| L1 资质真伪 | 公司真实、在营、规模多大？ | 工商登记、参保、注册资本 |
| L2 偿付能力 | 有没有钱还、赚不赚钱？ | **上市公司财报**（最硬）、营收、现金流 |
| L3 偿付意愿/习惯 | 过去拖不拖款？ | 司法判决、被执行、失信、欠税、票据违约 |
| L4 经营风险趋势 | 账期内会不会爆雷？ | 经营异常、股权冻结、涉诉量、行政处罚 |

**核心原则**：
- **上市公司财报是账期评估最硬的数据源**——权重最高（T1 财务 50%）
- **客户类型分层**：上市/民营中型/贸易小型/初创，数据可得性不同，权重必须切换
- **红线零容忍**：5 条硬红线（失信/破产/吊销/严重违法/经营异常）触发即阻断
- **账期硬约束**：建议账期 ≤ 客户自身应收周转天数——客户自己回款都不到这个周期，我们垫资必超其节奏
- **评分可追溯**：每维分数可追溯到真实数据，脚本驱动评分
- **数据诚实**：数据缺失不编造、数据矛盾不掩盖、软参数标"假设"

**覆盖范围**：上市企业（完整财务分析）+ 非上市企业（T2/T3/T4 降级策略，财务维度取中性分）。非上市企业评估仍可输出——但财务章节缩减且明确标注数据限制。

---

## 2. 场景与触发

**单一场景**：输入 1 家客户名称 → 输出账期评估报告（12 章 HTML）。

### 触发词清单

客户账期评估、客户信用评估、授信评估、账期评估、能不能放账期、给多少额度、客户付款风险、客户靠谱吗、评估一下这个客户、客户尽调、信用额度、账期建议

### 边界

- 本 Skill 做**单客户账期评估**，不做多客户横向对比
- 核心输出是"建议账期 + 建议额度 + 授信等级"，不是全面的供应商评审

---

## 3. 阶段 1：需求澄清（实体锚定 + 客户类型判定）

唯一的人机交互窗口。

### 3.1 实体锚定（必做）

```
1. 天眼查 search_companies → 确认完整登记名（消除简称歧义）
2. 天眼查 get_company_basic_profile → 确认工商信息 + 经营状态
3. 确认上市/非上市状态（天眼查 search_listed_companies）
```

多候选时必须由用户选择，禁止 AI 自动选第一条。

### 3.2 客户类型判定（必做）

按 `references/tier-weights.md` 判定 T1-T4：

```
上市？ → T1
营收 ≥5亿？ → T1
营收 5000万-5亿？ → T2
营收 <5000万 或 贸易型？ → T3
成立 <3年 或 营收 <1000万？ → T4
```

### 3.3 关注点确认（可选，用户说"开始吧"则跳过）

```
默认全面评估。用户可指定重点关注：
- 重点关注财务风险（上市客户）
- 重点关注付款记录（非上市客户）
- 重点关注经营稳定性（初创）
```

---

## 4. 阶段 2：深度采集（全部 MCP 双源）

按 `references/data-source-mapping.md` 的映射表，并发批次一次发所有工具调用。

### 4.1 采集维度

1. **工商基础**（P0 双源）：注册资本/信用代码/法人/成立日期/参保——天眼查 + 企查查
2. **财务数据**（上市 P1 双源）：营收/净利/毛利率/负债率/流动比/应收周转/现金流——Tushare + 东方财富
3. **风险数据**（P0/P1 双源）：失信/被执行/欠税/票据违约/经营异常/股权冻结/行政处罚——企查查 35 因子 + 天眼查
4. **需求盘子**：主营构成/前五供应商/招股书原材料构成——东方财富 + Tavily/AnySearch 提取
5. **舆情**：支付习惯/拖欠货款报道/海外声誉——博查 + Exa + TinyFish

### 4.2 纪律

- 企业查询先过天眼查 `search_companies` 实体锚定
- 企查查用完整登记名（禁止简称）
- **所有已装 MCP 必须全部参与**，不得只依赖天眼查/企查查
- 并发批次一次发所有工具调用，不逐批追加

---

## 5. 阶段 3：交叉验证（P0/P1 四级偏差）

按 `references/cross-validation-rules.md` 执行：

- 9 项 P0/P1 双源比对
- 偏差按四级协议处理（通过 / 偏差取保守值 / 单源标注 / 阻塞级中止）
- 阻塞级矛盾 → 中止评分，向用户报告，不静默跳过

---

## 6. 阶段 4：打分计算（F/R/S 三因子 + T1-T4 权重）

### 6.1 打分规则

完整规则见 `references/scoring-rules.md`，核心：

```
综合授信分 CS = w1·F(财务健康) + w2·R(信用风险) + w3·S(经营稳定性)
```

- **F 财务健康**（0-10）：偿债 3 + 盈利 2.5 + 现金流 2 + 增长 1.5 + 营运 1
- **R 信用风险**（0-10）：基础 10，扣被执行/欠税/票据违约/被诉
- **S 经营稳定性**（0-10）：基础 10，扣经营异常/股权冻结/实控人变更/高管异常/处罚/审计非标
- **T1-T4 分层权重**：非上市客户财务降权，信用+稳定升权
- **红线门禁**（5 条二进制）：触发 → 综合分置 None，阻断

### 6.2 脚本驱动

AI 填写原始分 → `scripts/credit_calculator.py` 加权计算 → 偏差 > 0.5 以脚本为准。

```
python scripts/credit_calculator.py <input.json> <output.json>
python scripts/credit_calculator.py --test    # 跑冒烟测试（20 用例）
```

### 6.3 输出

- 综合授信分 CS + 授信等级 S/A/B/C/D
- 建议账期（叠加 AR 硬约束）
- 建议授信额度（基于 PCB 需求盘子）

---

## 7. 阶段 5：需求盘子估算 + 对抗审查 + 报告渲染

### 7.1 PCB 需求盘子（额度依据）

按 `references/demand-estimation.md` 三方法估算，给区间不给单点。

### 7.2 对抗式审查（强制）

按 `references/adversarial-checklist.md` 过 8 条灵魂拷问，逐条记录 `question → evidence → verdict`。不通过不得渲染。

### 7.3 报告渲染

12 章 HTML 报告，品牌（`#059669` 翠绿 + 衬线字体）。模板：`assets/credit-assessment-report.html`。

报告结构：
0. 封面（授信等级徽章 + 建议账期 + 建议额度）
1. 授信结论（含 F/R/S 评分依据说明）
2. 客户基本面
3. 需求总体量摸排
4. 财务健康
5. 付款习惯与营运效率
6. 司法与信用风险矩阵
7. 经营稳定性
8. 风险信号矩阵
9. 授信结论与监控方案
10. 数据来源与验证状态
11. 报告说明 + 对抗审查记录

**报告铁律**：禁止出现 MCP 工具名/脚本名/函数名；无占位符残留；数据缺失用空字符串，不填占位。
