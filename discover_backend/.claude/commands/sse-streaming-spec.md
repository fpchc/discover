# SSE 流式输出与打字机效果

## 适用场景 / 何时触发

- 实现对话接口、事件编码、打字机节流时
- 前端消费事件流、渲染思考分区与正文分区时
- 排查流式中断、无输出、输出成块而非逐字、代理超时断连时

---

## 1. 硬约束

| # | 约束 | 说明 |
|---|------|------|
| 1 | 对话接口对齐 chat-messages 契约 | `POST /chat-messages`；`response_mode=streaming` 走 SSE（`event` 判别帧，以 message_end 收尾，无 `[DONE]`）；`blocking` 返回 JSON |
| 2 | 正文必须逐字符节流推送 | 模型分片是成块到达的，直接透传是「块状跳变」，不是打字效果 |
| 3 | 思考内容不进正文 | 流无法分区渲染，思考增量只作内部事件，不进入 `message` 帧的 `answer` |
| 4 | 必须有心跳 | 无数据期超过代理超时会断连；心跳帧为 `event=ping` |
| 5 | 必须禁用代理缓冲 | 不禁用则整条流被缓冲到结束才下发，流式完全失效 |
| 6 | 审批已整体移除 | 无审批节点 / 事件 / 接口，工具调用直接执行 |

---

## 2. 为什么需要自己做节流

模型流式返回的分片粒度不均：可能一次返回一个字，也可能一次返回几十个字。直接把分片转发给前端，用户看到的是「卡顿式成块出现」，与常见对话产品的均匀打字效果差异明显。

正确做法是在服务端加一层**节流队列**：

```
模型分片（不均匀，成块）
      ↓
   字符缓冲区（累积待输出字符）
      ↓
   定时取出固定字符数
      ↓
   逐帧推送（间隔均匀）
      ↓
前端追加渲染 → 均匀打字效果
```

**节流放服务端而非前端的理由**：前端节流需要缓存全部未显示内容，若用户中途关闭页面，已生成内容与已显示内容不一致，恢复会话时状态难对齐。服务端节流让「已推送」等于「已显示」。

---

## 3. 节流参数

| 参数 | 作用 | 取值考虑 |
|------|------|---------|
| 帧间隔 | 每次推送的时间间隔 | 太长显得迟缓，太短产生大量小帧增加开销 |
| 每帧字符数 | 单帧推送的字符数量 | 与帧间隔共同决定视觉速度 |
| 追赶阈值 | 缓冲区积压超过此值时提速 | 防长回答时输出严重滞后于生成 |
| 追赶倍率 | 提速时每帧字符数的放大倍数 | 避免结尾大段瞬间刷出 |
| 收尾策略 | 模型已结束但缓冲区仍有内容 | 允许提速但不允许一次性倒完 |

全部走配置，不硬编码。思考内容与正文可用不同参数组——思考通常更长，可用更快的推送节奏。

**追赶机制是必需的**：模型生成速度常快于设定的打字速度，长回答会让缓冲区持续积压。若不追赶，模型早已结束而前端还在慢慢打字，用户体验为「卡住了」。

## 4. 中英文与特殊字符

按字符切分会遇到几类问题，必须处理：

| 情况 | 处理 |
|------|------|
| 多字节字符 | 按字符切分而非字节切分，禁止切开一个字符 |
| 组合字符（表情、变音符） | 按字素簇切分，避免拆出无意义半个符号 |
| Markdown 结构符号 | 允许中途切开（前端渐进渲染时会短暂显示原始符号，可接受） |
| 代码块 | 同上，前端应在代码块未闭合时按纯文本渲染 |

**不要为了「Markdown 完整性」而缓冲到语法结构闭合再推送**——这会让代码块一次性整块出现，破坏打字效果，且长代码块会造成长时间无输出。

## 5. 事件类型

事件流是前端与平台的唯一契约。前端不感知智能体内部、不感知 MCP、不感知图结构。

| 事件语义 | 载荷要点 | 前端表现 |
|---------|---------|---------|
| 智能体选定 | 智能体 ID、显示名、理由、置信度 | 顶部标识当前智能体 |
| 技能选定 | 技能 ID、理由 | 副标识 |
| 工具就绪 | 核心工具数、目录规模、已启动服务 | 工具面板 |
| 思考开始 | — | 打开思考分区 |
| 思考增量 | 文本增量 | 思考分区追加 |
| 思考结束 | 思考耗时 | 折叠思考分区 |
| 正文增量 | 文本增量 | 正文追加（打字机） |
| 工具调用发起 | 调用标识、工具名、参数摘要 | 折叠卡片，加载态 |
| 工具调用完成 | 调用标识、成败、结果摘要、耗时、是否截断 | 卡片定状态 |
| 门禁校验 | 门禁 ID、是否通过、失败项 | 门禁进度 |
| 数据源降级 | 来源、原因、降级说明 | 告警条 |
| 产物就绪 | 产物标识、文件名、类型、大小、下载地址 | 下载卡片 |
| 错误 | 类别、消息、是否可恢复、建议 | 错误块 |
| 完成 | 轮次、总耗时、用量 | 恢复输入框 |
| 心跳 | — | 忽略 |

事件模型用 pydantic 判别联合，以事件类型作判别字段。当前对外契约是
chat-messages 流（§6），富事件仅作内部驱动：`text_delta` 映射为 `message`
帧的 `answer`，心跳映射为 `ping`，`done` 触发 `message_end`（含 usage），
错误映射为 `error`；其余事件（路由/思考/工具/产物）在对外流中丢弃。
带富事件的前端在 P1 未实现。

**每个事件必须带单会话内单调递增的序号**（内部排序去重；对外帧不携带）。

## 6. 传输细节

| 项 | 要求 |
|---|------|
| 帧格式 | 事件判别帧：`data: {json}\n\n`，`event` 判别字段；`message`（正文增量）、`message_end`（收尾，含 metadata.usage 与 conversation_id）、`ping`（心跳）、`error` |
| 会话标识 | `conversation_id` 经帧内字段与响应头 `X-Conversation-Id` 返回（自动创建时客户端凭此续聊） |
| 响应头 | 声明事件流类型、禁用缓存、**显式禁用反向代理缓冲** |
| 心跳 | 周期小于代理超时（常见代理默认几十秒），可用注释帧或专用心跳事件 |
| 客户端断开 | 检测到断开立即取消图执行任务，并释放会话资源 |
| 资源释放 | 必须放在异常安全的收尾分支，异常路径也要执行 |

**禁用代理缓冲是最容易漏的一项**。多数反向代理默认会缓冲响应体，导致整条流积压到结束才一次性下发，前端表现为「等很久然后全部出现」。

---

## 7. 背压与丢弃策略

事件队列必须有界。队列满时按事件重要性区分处理：

| 事件类别 | 满时策略 |
|---------|---------|
| 正文增量、思考增量 | 可合并（把多个增量拼成一个），不可丢弃内容 |
| 心跳 | 可丢弃 |
| 工具调用、工具完成、产物、错误 | **不可丢弃、不可合并**，必须背压等待 |
| 完成事件 | 不可丢弃 |

**增量合并而非丢弃**：丢弃增量会导致用户看到的文本缺字，属于数据错误；合并只影响打字节奏，可接受。

---

## 8. 审批往返

**已移除**（用户决策 2026-08）。无审批节点 / 事件 / 接口 / 策略；工具调用直接执行，
不存在跨请求挂起与会话泄露问题。

---

## 9. 脱敏

事件流可能被日志、代理、浏览器扩展记录，脱敏必须在推送前完成，不能指望前端不显示。

| 内容 | 处理 |
|------|------|
| 工具参数摘要 | 截断；按键名匹配敏感词（令牌、密钥、口令、认证、凭据类）的值替换为遮蔽符 |
| 错误消息 | 不含完整命令行、不含环境变量值、不含请求体 |
| 降级原因 | 不含凭据 |
| 产物下载地址 | 用不可枚举的标识，不含会话 ID 与原始文件名 |

- [ ] 心跳周期小于代理超时
