# 多智能体平台架构判定规范

## 适用场景

- 新增或调整顶层模块、目录、依赖方向
- 判断能力属于平台、运行时、基础设施还是智能体包
- 评审跨模块改动半径

## 不适用场景

- 查询当前文件路径或现有模块清单
- 修改单一技术组件的实现细节

## 职责边界与权威来源

本文件只定义稳定的架构判定原则，不保存易变化的目录快照、当前服务状态或分期进度。

- 当前架构事实：`.ai/ARCHITECTURE.md`
- 职责与文件路径：`.ai/MODULE_MAP.md`
- 智能体包格式：`agent-package-spec.md`
- 技能装配：`skill-assembly-spec.md`
- MCP、工具、LLM、SSE、脚本：对应专项规范

## 1. 平台边界

平台提供通用承载能力：HTTP 接入、运行时编排、工具接入、会话与隔离、事件流、持久化、配置和可观测性。

平台不承载具体行业知识、智能体工作流、评分规则、报告模板或技能专属脚本。

**判定问题**：换一个智能体后仍然需要的能力，才可能属于平台；仅某个智能体需要的内容归智能体包。

## 2. 分层与依赖方向

当前分层名称以 `.ai/ARCHITECTURE.md` 为准，稳定依赖原则为：

```text
interfaces → domain / runtime / capabilities → infrastructure → shared / config
bootstrap 只做组合根，可组装所有层，但不承载业务逻辑
```

- `interfaces`：协议适配、鉴权、请求响应和事件编码，不实现业务规则。
- `domain`：业务用例与领域契约，不依赖 FastAPI 路由或具体基础设施。
- `runtime`：Agent 状态机、阶段编排、策略、门禁、预算与生命周期。
- `capabilities`：LLM、工具、MCP 等可调用能力及其抽象。
- `infrastructure`：数据库、Redis、存储、日志等技术实现。
- `bootstrap`：依赖注入与生命周期组装。
- `shared / config`：少量跨层稳定契约与配置；不得变成杂物间。

禁止反向 import。跨层调用依赖调用方拥有的 `Protocol` / `ABC`，具体实现只在组合根装配。

## 3. 平台与智能体隔离

- 平台代码不得硬编码智能体 ID、技能 ID、具体工具名、模板名或业务规则。
- 智能体包不得 import 平台内部模块；脚本仅通过标准流、文件契约和白名单环境变量交互。
- 平台与智能体包的静态耦合面只有 AGENT / SKILL 清单及其声明的资源契约。
- 智能体之间不得直接读写对方目录或共享可变状态；协作必须由平台显式传递结构化结果。
- 工作区、工具命名空间、产物和会话数据必须按既定隔离键管理。

## 4. 流程控制归属

- 多阶段业务流程由 LangGraph 状态机、Policy、Contract 和脚本校验器控制。
- 提示词负责角色、语义判断与输出要求，不承担可确定执行的流程跳转、预算或重试计数。
- Runtime 不直接识别具体 MCP、脚本或智能体；只依赖装配计划和工具抽象。
- 装配层负责“计算计划”，运行时负责“执行计划”，工具代理负责“目录与分发”。

## 5. 放置决策

新增内容时依次判断：

1. 是否为某一 feature 的单一业务动机？是则与相关路由、Service、模型和测试就近放置。
2. 是否为跨 feature 的稳定契约？是则提炼最小抽象，避免共享业务实现。
3. 是否为外部技术实现？放基础设施或能力适配层，不泄漏到核心业务。
4. 是否只负责组装？放 bootstrap，不把业务判断带入组合根。
5. 是否会迫使多个不相关模块同时修改？若会，先重新划分边界。

## 6. 架构变更要求

- 先确认依赖方向与改动半径，再修改代码。
- 新增跨层契约必须明确所有者和唯一修改理由。
- 目录、模块职责或关键决策变化后，同步更新 `.ai/ARCHITECTURE.md` 与 `.ai/MODULE_MAP.md`。
- 不在本文件记录端口、当前提供方、启用状态、阶段进度和临时迁移说明。

## 7. 本规范专属检查

- [ ] 新代码归属可用一个明确修改理由解释
- [ ] 无反向 import、跨智能体目录访问或具体业务字面量渗入平台
- [ ] 核心业务仅依赖抽象，具体实现位于适配或组装层
- [ ] 流程控制未退化为提示词中的自然语言步骤
- [ ] 架构事实源已在结构变化后同步
